## 一、底层改造：转写结果结构化

### 现状

`asr_engine.py` 的 `_parse_result()` 把结果拼成纯文本，丢失了 `start_ms/end_ms/spk` 结构。

### 改造

`ASREngine.transcribe()` 返回结构化对象：

```python
{
  "sentences": [
    {"start_ms": 0, "end_ms": 30000, "speaker": 1, "text": "不要打车，自觉维护交通秩序。"},
    {"start_ms": 30000, "end_ms": 35000, "speaker": 1, "text": "正好在直播……"},
  ],
  "speakers": {          # 编号 → 显示名（用户可编辑）
    1: "说话人1",
    2: "说话人2"
  }
}
```

- `speaker` 用数字编号，`speakers` 映射编号 → 显示名，便于改名/合并
- 保留 `to_text()` 方法转回纯文本（给 AI 总结、导出用）
- 历史记录存结构化 `transcript.json`（时间戳可点、改名保留）

## 二、需求 1：启动即预加载模型

### `ModelManager`（单例，模型常驻）

现状问题：`TranscriptionWorker.run()` 每次新建 `ASREngine` + `load_model()`，线程结束 engine 销毁 → 每次转写都重新加载约 60 秒。

改为全局唯一 engine 常驻复用：

```
ModelManager（单例）
├─ engine: ASREngine（唯一实例）
├─ state: idle | loading | ready | failed
├─ load_async(): 后台线程加载
└─ get_engine(): 就绪后返回
```

### 启动流程

```
main() 启动
├─ 显示主窗口（立即，不阻塞）
├─ ModelManager.load_async() 后台加载
│    └─ 状态栏：「模型加载中…」→「✅ 模型已就绪」
└─ 用户可先配置 / 看历史记录
```

### 转写协调 + 线程安全

- 已就绪 → 直接转写（零等待）；加载中 → 等就绪信号；失败 → 转写时重试
- funasr 推理非线程安全，加锁串行化
- **已确认**：接受启动即占 2-3GB 显存/内存换转写零等待

## 四、需求 3：历史记录

### 数据模型

```
records/<id>/
├─ meta.json          # 元信息（标题/时间/时长/来源/状态）
├─ audio.wav          # 音频副本（16k 单声道，播放 + 转写对齐）
├─ transcript.json    # 结构化转写结果
└─ summary.md         # 会议纪要（有则存）
```

`records/index.json` 总索引：

```json
{
  "records": [
    {"id": "20260828_201500_a1b2", "title": "房东签约沟通",
     "created_at": "2026-08-28T20:15:00", "duration_sec": 285.75,
     "source": "recorded", "status": "transcribed"}
  ]
}
```

### 状态机

```
pending      → 仅音频，未转写
transcribed  → 有转写，无纪要   ←「转写了但没做纪要」
summarized   → 有纪要
```

### 交互闭环

1. 录音停止 → 自动新建记录（pending）
2. 导入文件 → 自动新建记录（pending）
3. 转写完成 → 写 transcript.json，status → transcribed
4. 生成纪要 → 写 summary.md，status → summarized
5. 点历史记录 → 加载音频 + 转写 + 纪要 → 补纪要/导出/播放
6. 删除记录 → 删目录 + 索引条目

### 存储（已确认）

- **每条记录复制一份 16k wav**（约 7MB/分钟，1 小时 ≈ 420MB）
- 提供「清理音频、只留文本」选项

### 旧录音迁移（已确认：要迁移）

- **实际现状**：工程根 `recordings/` 目录为**空**，`dist/MeetingAssistant/recordings/` 也不存在 —— 当前无实际旧录音需迁移
- **但迁移逻辑仍要写**（防御性、兼容未来）：首次运行新版时扫描旧 `recordings/*.wav`，自动转成历史记录（status 按是否有同名转写/纪要文件判断，通常是 `pending` 或 `transcribed`）
- 迁移后保留原文件（不删源，避免误删）

## 五、需求 4：录音播放 + 需求 5：时间戳跳转

### 技术选型（已验证）

`PyQt6.QtMultimedia` 可用：`QMediaPlayer` + `QAudioOutput`。

### 播放控制条（底部）

```
[▶ 播放] [⏸ 暂停] [⏹ 停止]   [━━━━━━━进度条━━━━━━━]  00:00 / 04:45
```

### 时间戳跳转

- 每条句子一个可点击时间戳（如 `[00:00:30]`）
- 点击 → `player.setPosition(start_ms)` → 从对应位置播放
- 播放中当前句自动高亮
- **已确认**：播放用转写用的 16k wav（时间戳绝对精确对齐，牺牲一点音质）

### 打包注意（风险点）

- `QtMultimedia` 需额外收集 Qt 插件（`mediaservice`、`audio`）+ DLL
- `build_exe.spec` 加 `collect_all('PyQt6.QtMultimedia')`
- wav 是未压缩 PCM，Windows 走 Media Foundation，无解码器风险
- **这是最大新增风险点，需重点验证打包后播放是否正常**

## 六、需求 6：转写结果可编辑说话人

### 方案：重命名 + 合并（默认，更实用）

用户核心诉求通常是「把说话人1改成张三」「把两人合并成同一人」。

**交互**：
1. 每条句子右侧显示说话人标签（如 `说话人1`）
2. 点击标签 → 编辑框，可：
   - **重命名**：输入姓名 → 该说话人所有句子统一更新
   - **合并**：选「与说话人X合并」→ 两编号合并为一
3. 改名/合并后：转写区实时刷新 + 存回 `transcript.json` 的 `speakers` 映射
4. **生成纪要时** AI 收到的文本自动用新名字（张三/李四 替代 说话人1/2）

### 数据结构

```python
# speakers 映射
{1: "张三", 2: "李四"}

# 合并：编号 2 并入 1
# 所有 speaker==2 的句子改为 1
```
