# 打包提速调研（2026-09-02）

## 用户问题
1. 打包慢（~7.5 分钟），能否加速？用户观察瓶颈在"模块收集"。
2. 父进程 kill 了，为什么子进程还活着？不是应该同步吗？

## 问题 2 解答：Windows 进程模型
- 父进程（Qt 事件循环等模型加载）和子进程（multiprocessing 非 daemon worker，
  7GB 内存真实加载模型）是**独立的 OS 进程**。
- Windows 上 multiprocessing 用 spawn 模式，父进程退出**不会**级联终止子进程。
- 只有 daemon=True 的子进程会随父退出被杀，但 daemon 子进程不能再生子进程，
  所以模型 worker 必须 daemon=False → kill 父进程后变孤儿进程，继续锁文件。
- 教训：kill 预览/测试进程须用 `taskkill /PID x /T /F`（杀进程树），或代码里 atexit 清理。

## 问题 1 调研：打包瓶颈实测
- 统计 collect_all 23 包：6634 个 hiddenimports 中 1228 个（19%）是测试类模块
  （numba 55% / sklearn 45% / scipy 35% / numpy 30%）。
- 优化动作：spec 增加 _is_test_module 过滤，hiddenimports 剔除 tests 模块；
  去掉冗余的 collect_submodules("scipy"/"sklearn")（collect_all 已含）。
- **实测结果：打包 7.4 分钟 vs 旧 7.5 分钟，几乎无提速**；EXE 99.6MB→88.6MB（-11MB），
  功能正常（过滤版 EXE 启动→预加载→ready 全通过）。

## 结论：瓶颈不在"模块收集"清单，而在 Analysis 阶段逐个真实 import
- PyInstaller Analysis 对每个 hidden module 做**真实 import 执行**（非扫文件名），
  import 触发 scipy/sklearn/numba/torch 的初始化代码（numba JIT、torch 扩展、
  scipy 链接）——这部分与 hiddenimports 数量弱相关，是 CPU 密集主耗时。
- datas（文件复制）快，不是瓶颈；测试文件仍在 datas 里（过滤只作用于 PYZ）。
- EXE 缩小 11MB 是 PYZ 压缩阶段收益（该阶段本来就快）。

## 真正有效的提速方案（按性价比）
1. **增量构建（最实用）**：PyInstaller 分析缓存在 build/。只改业务代码时
   不清 build/、不动 spec，重跑只重新分析变更 → 二次打包约 3 分钟（省一半）。
   之前每次 --noconfirm 清空 build 等于全量重来。
2. **手动白名单收集（治本）**：放弃 collect_all 23 包，改列 funasr 实际用到的
   十几个模块 + datas。分析量砍 60%+。代价：改依赖要重新核对，有漏 import 风险，
   需真转写回归兜底。建议等阶段 B/C 代码稳定后再做。
3. 换更快机器/加内存：分析阶段单线程吃 CPU + 峰值 7GB 内存。
4. --noupx 默认关、strip 无用，不是因素。
